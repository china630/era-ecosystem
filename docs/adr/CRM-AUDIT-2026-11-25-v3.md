## 5. Новые и оставшиеся дефекты кода

### 5.1 Обход record-level scope через `?ownerId=` (новый, в свежем коде)

`nest/generated/leads.ts`:

```ts
const scopeWhere = userId ? await leadScopeWhere(organizationId, userId, scope) : { organizationId };
const where = { ...scopeWhere };
if (mine && userId) where.ownerId = userId;
else if (ownerId) where.ownerId = ownerId;
```

`leadScopeWhere` для `own`/`group` уже ставит `ownerId` (`userId` или `{ in: ownerIds }`). Потом `where.ownerId = ownerId` из query **перезаписывает** фильтр. Агент с `LEADS_READ` и scope `group`/`own`, передав `?ownerId=<чужой user id>`, получает лиды этого владельца даже вне группы. `mine=true` безопасно (сужает до себя).

Дополнительно: `resolveLeadScopeFromGrants` даёт `all` не только owner/`LEADS_ASSIGN`/`ACCESS_MANAGE`, но и `LEADS_EXPORT`. Дефолт без этих грантов — `group` (не `own`); при членстве в широкой группе это ближе к «все лиды».

### 5.2 Scope не доведён до соседних API (остаток P0-7)

- `POST /api/visits` (`nest/generated/visits.ts`): `findLeadById(leadId)` без `assertLeadInScope` и без `organizationId`. `visits.service.ts` — `prisma.lead.findUnique({ where: { id } })`. Можно привязать визит к чужому/внешнему лиду, если id известен.
- `GET /api/visits`: `listVisitsRecent()` без явного scope (и без явного `organizationId` в сервисе — тенант, если есть, только через middleware). `include: { lead: true }` отдаёт карточку лида.
- Старый `POST /api/inbox` — та же схема с `findLeadById`.
- `GET /api/calls?leadId=` и `POST /api/tasks` (с `leadId`) в `integrations-routes.ts` не вызывают `requireLeadScope`.

### 5.3 Сервер всё ещё принимает секрет виджета в query

`packages/integrations-kit/src/providers/webchat.ts` и общий `verifyWebhook` в `_factory.ts`: при несовпадении заголовка проверяется `req.query.k`. Старый клиент или ссылка с `?k=` снова светит секрет в логах прокси и Referer.

### 5.4 Прочее (не регресс закрытых пунктов)

- Окно 24 ч не действует для Instagram / Facebook Messenger / Viber.
- WeChat-challenge (`echostr`): достаточно наличия `verifyToken`, подпись не проверяется.
- `PATCH /api/leads/:id/assign`: `findUserById(body.ownerId)` без `organizationId` — владельцем можно назначить пользователя другого тенанта.
- Смена стадии в `leads.service.ts` по-прежнему не запускает pipeline-lite (`P1-1`).
- Orch WhatsApp и каталожные стабы — см. §2.
- Мелочь: BullMQ `queue.add("drain")` без стабильного `jobId` при каждом старте процесса может размножить repeatable jobs; двойной send теперь режет атомарный claim.

Сломанных импортов/типов в изменённых файлах не видно. UI не бьёт в отсутствующие эндпоинты: тост → `/api/realtime/calls`, инбокс → `/api/conversations` и `POST .../messages` (все зарегистрированы). Ключи i18n `callsRealtime` и `inbox.outsideWindow` / `sendTemplate` есть в en/ru/az.
